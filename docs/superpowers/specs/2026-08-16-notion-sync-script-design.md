# Notion 동기화를 MCP에서 Python 스크립트로 전환 — 설계

- 작성일: 2026-08-16
- 상태: 설계 확정, 구현 전
- 대상: `CLAUDE.md` §6 전체

## 1. 배경과 문제

현재 §6 동기화는 Claude 세션의 Notion MCP 호출로 수행한다. 두 가지가 걸린다.

**비용.** MCP는 본문을 tool 파라미터로 인라인 전달해야 하므로 모든 페이지 본문이
에이전트의 출력 토큰을 통과한다. §6.4는 2026-08-15 최초 동기화에서 겪은 실패를
규칙으로 박아 두었다 — `\uXXXX` 이스케이프로 문자 수 2.24배 팽창, 형식 오류로
8회 실패·97 KB(코퍼스의 42%)·8턴 소모. **이 규칙들은 전부 "에이전트가 본문을
출력한다"는 전제 위에서만 필요하다.**

**환경 종속.** §6 제약이 "Notion MCP가 연결된 Claude 세션에서만 가능"이다.
Codex 등 다른 에이전트는 동기화를 시도조차 할 수 없다.

여기에 2026-08-16 시점의 사실이 하나 더해졌다 — **사용자가 Notion 쪽 페이지를
전부 삭제했다.** DBA 부모 페이지는 살아 있으나 비어 있고, §6.1 컨테이너와 32개
지식 페이지(전체 35개 중 동기화 이력이 있는 것)가 모두 휴지통에 있다.

## 2. 결정적 사실 — 공식 API가 Notion-flavored Markdown을 받는다

조사 결과 전환 비용이 예상보다 훨씬 낮다.

| 용도 | 엔드포인트 |
|---|---|
| 신규 생성 | `POST /v1/pages` — `{parent:{page_id}, properties:{title}, markdown:"..."}` |
| 본문 조회 | `GET /v1/pages/:page_id/markdown` |
| 본문 교체 | `PATCH /v1/pages/:page_id/markdown` — `{type:"replace_content", replace_content:{new_str}}` |

- 헤더: `Authorization: Bearer <token>`, `Notion-Version: 2026-03-11`, `Content-Type: application/json`
- `<callout>`·`<table>`·`<mention-page>` 등 XML 태그를 그대로 지원한다
- `markdown` 필드는 `children`/`content`와 상호 배타

**그래서 `scripts/notion-convert.py`의 출력이 곧 API 입력이다.** 변환기를 다시 쓸
필요가 없고, 외부 의존성 없이 stdlib `urllib.request`로 충분하다.

리스크 1건도 해소됐다 — 변환기가 내는 self-closing `<mention-page url="..."/>`가
Notion 자신의 출력 형태와 동일함을 실제 페이지 조회로 확인했다.

출처:
- https://developers.notion.com/guides/data-apis/working-with-markdown-content
- https://developers.notion.com/guides/data-apis/enhanced-markdown
- https://www.notion.com/releases/2026-05-13

## 3. 범위

**한다**: 증분 판정 → 배치 결정 → 변환 → HOLD 검사 → 업로드 → 스탬프 → 로그 기록까지
스크립트가 전부 수행한다. 판단이 필요한 건만 중단하고 사람에게 넘긴다.

**하지 않는다**: Notion → wiki 역방향 회수(단방향 원칙 유지), Notion 쪽 편집 병합,
페이지 삭제, 데이터베이스/속성 조작.

## 4. 구성

| 파일 | 상태 | 역할 |
|---|---|---|
| `scripts/notion-sync.py` | 신규 | 단일 진입점 |
| `scripts/notion-convert.py` | 변경 없음 | `convert()` 재사용 |
| `scripts/notion-stamp.py` | 변경 없음 | `stamp()` 재사용 |
| `scripts/notion-tree.json` | 신규(커밋) | 컨테이너 이름 → page_id |

파일명이 하이픈이라 일반 import가 불가능하다. `importlib.util.spec_from_file_location`
으로 로드한다 — 파일명을 바꾸면 `CLAUDE.md` §6.4의 스크립트 참조가 깨지므로 이쪽을 택한다.

### CLI

```
python3 scripts/notion-sync.py [옵션]

  (무옵션)                  §6.3 증분 동기화
  --dry-run                 계획만 출력, HTTP 호출 0
  --only <slug>...          지정 페이지만. §6.3 "강제 재업로드는 사용자가 페이지를 명시"
  --force-replace <slug>... HOLD를 무시하고 덮어씀
  --init-tree               DBA 아래 컨테이너 생성 + notion-tree.json 기록 (1회성)
  --refresh-tree            기존 컨테이너를 재탐색해 notion-tree.json 갱신
  --reset-stamps            전 페이지 notion_page_id·notion_synced를 null로 (1회성)
```

**전 페이지를 대상으로 만드는 플래그는 만들지 않는다.** §6.3의 "전체 재업로드 금지"를
코드 수준에서 강제한다. 기본 실행도 호출 전에 전체 계획을 먼저 출력한다.

## 5. 데이터 흐름

```
wiki/*.md frontmatter
  │
  ├─(§6.3)─> notion_synced == null 또는 updated >= notion_synced[:10] ?
  │            └─ 아니오 ──> [skip]
  │
  ├─(§6.1)─> index.md 분류 절 + tags ──> 부모 page_id
  │            └─ 판정 불가 ──> [HOLD]
  │
  ├────────> notion_convert.convert() ──> Notion-flavored Markdown
  │
  ├─[기존]──> GET /v1/pages/:id/markdown ──> 절 제목 차집합
  │            └─ Notion 전용 절 존재 ──> [HOLD] (업로드하지 않음)
  │
  ├────────> POST /v1/pages  또는  PATCH /v1/pages/:id/markdown
  │
  └─[성공 즉시]─> frontmatter stamp ──> log.md 맨 위 SYNC_NOTION 한 줄
```

스탬프는 **페이지 단위로 즉시** 쓴다. 마지막에 몰아 쓰면 중간 실패 시 어디까지
올렸는지 알 수 없어 다음 실행이 전량 재업로드가 된다 (§6.3).

## 6. 판정 로직

### 6.1 인증

`NOTION_API_KEY`. 환경변수가 있으면 우선, 없으면 볼트 루트 `.env`에서 읽는다.

실행 전 두 가지를 확인하고 어기면 **즉시 종료**한다.

1. `git ls-files --error-unmatch .env`가 성공하면(= 추적 중) 중단
2. `.env`의 퍼미션이 `600`이 아니면 중단

토큰 값은 로그·에러·계획 출력 어디에도 찍지 않는다. `.env`는 이미 `.gitignore`에 있다.

### 6.2 증분 판정 (§6.3 그대로)

```
notion_synced == null                  -> 대상
updated >= notion_synced[:10]          -> 대상
그 외                                   -> 건너뜀
```

날짜 10자로 자른 문자열 비교이며 `>`가 아니라 `>=`다. `>`로 하면 같은 날 동기화한
뒤 수정한 페이지가 영원히 누락된다 — 2026-08-15에 13개 중 12개가 실제로 빠졌다.

### 6.3 배치 (§6.1) — index.md에서 파생

**컨테이너 트리** (총 16개, 이 중 페이지를 받는 부모는 13개):

```
DBA (3aefb969b8be801280b8dc2ff35fbefb)
├── db운영
│   ├── MySQL              *
│   ├── PostgreSQL         *
│   ├── SQL Server         *
│   ├── Aurora DSQL        *
│   └── 엔진 공통
│       ├── 엔진 비교       *
│       ├── 진단·운영 표준   *
│       ├── 보안·권한       *
│       ├── 개발·자동화     *
│       └── 지식 운영       *
├── 업무기록
│   └── kakaogames         *
├── 개인                    *
├── 참고자료                 *
└── 종합원칙                 *
```

`*` = 페이지를 받는 부모. `db운영`·`엔진 공통`·`업무기록`은 중간 노드이며
그 바로 아래에 지식 페이지를 두지 않는다.

**절 → 부모 매핑.** `index.md`에서 각 slug가 처음 등장하는 분류 절을 찾는다.
index의 절 이름과 Notion 컨테이너 이름이 일부 다르므로 매핑표를 둔다.

| index.md 절 | Notion 부모 |
|---|---|
| `### 엔진별 운영` | 태그 분기 (아래) |
| `### 진단·운영 표준` | 진단·운영 표준 |
| `### 보안·권한` | 보안·권한 |
| `### 개발·자동화` | 개발·자동화 |
| `### 지식 운영` | 지식 운영 |
| `## 업무 기록` | kakaogames |
| `## 개인` | 개인 |
| `## 참고자료` | 참고자료 |
| `## 종합·원칙` | 종합원칙 |

**분류 절이 아닌 곳의 링크는 무시한다.** 특히 `## 미완 과제 (건강검진 추적 대상)`은
17개 링크를 갖고 있어 제외하지 않으면 대부분의 페이지가 오배치된다. 절 밖(Takeaway·부제)의
링크도 무시한다. 매핑표에 없는 절 이름을 만나면 **실패**시킨다 — 조용히 배치하지 않는다.

**엔진 분기.** `엔진별 운영` 절에 한해 `tags`로 순차 판정한다.

```
1. tags에 dsql 있음                              -> Aurora DSQL
2. {mysql, postgresql, sqlserver} 교집합 크기 2+  -> 엔진 비교
3. 교집합 크기 1                                  -> 해당 엔진
4. 교집합 크기 0                                  -> 엔진 비교
```

**`aurora`는 라우팅 키가 아니다.** 호스팅 변종 표식일 뿐이며, §6.1의 "관리형 변종은
원 엔진으로 묶는다"는 항상 함께 붙는 `mysql`·`postgresql` 태그가 이미 표현한다.
`aurora`를 키로 쓰면 `aurora-dsql`이 MySQL로, `cloud-platform-knowledge`가
MySQL로 잘못 간다 — 설계 중 실제 데이터로 확인한 오류다.

이 규칙은 `엔진별 운영` 절 12개 전부에 대해 검증했다.

### 6.4 HOLD 검사 (§6.2 대체)

기존 §6.2는 "Notion에만 있는 절은 지우지 않고 남긴다"였다. `replace_content`는
페이지를 통째로 덮으므로 이 규칙과 충돌한다. 그리고 §6.2 주석이 이미 경고했듯,
남겨둔 절은 `wiki/`에 없으므로 건강검진의 모순·stale 점검이 닿지 않는다.

**새 규칙**: 업로드 전 `GET /markdown`으로 현재 본문을 받아 `^#{2,}` 절 제목 집합을
뽑고, 위키 변환 결과의 절 제목 집합과 차집합을 낸다. Notion에만 있는 절이 하나라도
있으면 **업로드하지 않고** 절 제목을 그대로 보고한다.

해소 방법은 둘 중 하나다 — 그 절을 `wiki/`로 옮겨 적고 재실행하거나,
`--force-replace <slug>`로 폐기한다. 스크립트가 임의로 고르지 않는다.

### 6.5 실패 처리

- 429·5xx는 지수 백오프 3회 재시도
- 페이지 단위로 독립이며, 한 건의 실패가 나머지를 막지 않는다
- **실패한 페이지는 스탬프하지 않는다** → 다음 실행에서 자동으로 다시 대상이 된다
- 4xx(권한·검증 오류)는 재시도하지 않고 해당 페이지만 실패 처리

### 6.6 페이지 제목과 아이콘

제목은 frontmatter `title`을 그대로 쓴다. 삭제 전 Notion 페이지에는 이모지 아이콘이
있었으나 위키 스키마에 대응 필드가 없으므로 **아이콘은 설정하지 않는다.**
필요해지면 frontmatter에 필드를 추가하는 것이 먼저다.

## 7. 전환 계획 — Notion 페이지 삭제 반영

삭제로 인해 "증분 동기화" 전제가 깨졌다. 1회성 초기화 경로가 필요하다.

**가장 위험한 지점**: 휴지통의 페이지는 **여전히 유효한 ID로 조회된다**(`deleted` 플래그가
붙은 채). `notion_page_id`를 리셋하지 않으면 스크립트가 휴지통 페이지를 갱신 대상으로
잡아 되살리려 든다.

| 단계 | 명령 | 내용 |
|---|---|---|
| 0 | (사용자) | Notion integration 생성 → **DBA 페이지에 연결** → `.env`에 `NOTION_API_KEY` |
| 1 | `--reset-stamps` | 32개 `notion_page_id`·`notion_synced` → `null` |
| 2 | `--init-tree` | 컨테이너 16개 생성 → `notion-tree.json` 기록 |
| 3 | `--only aurora-dsql` | 카나리 1건. 변환·배치·mention 링크를 눈으로 확인 |
| 4 | (기본 실행) | 나머지 34개 생성 |

3단계 카나리를 두는 이유는, 34개를 올린 뒤 변환 문제를 발견하면 34개를 다시 손봐야
하기 때문이다. 4단계 이후로는 §6.3 증분 동기화가 정상 작동한다.

**교차참조 주의** — `notion-convert.py`는 대상의 `notion_page_id`가 있을 때만 mention을
낸다. 초기 생성 중에는 아직 ID가 없는 페이지가 백틱으로 남는다. 전부 생성된 뒤
**한 번 더 전량 갱신이 필요**하다. 이때 `updated`가 그대로면 §6.3이 건너뛰므로,
초기 구축에 한해 `--only`로 대상을 명시해 2차 패스를 돈다.

## 8. CLAUDE.md §6 개정 범위

| 절 | 조치 |
|---|---|
| §6 서두 제약 | "Notion MCP가 연결된 Claude 세션에서만 가능" 삭제. 토큰이 있으면 어느 에이전트에서도 가능 |
| §6.1 | 유지. 배치 규칙이 곧 스크립트 매핑표의 근거다. 태그 분기 규칙을 명문화 |
| §6.2 | 병합 규칙을 HOLD 방식으로 교체 |
| §6.3 | 유지. 판정식이 코드로 옮겨질 뿐 규칙은 동일 |
| §6.4 | 4개 비용 규칙은 에이전트가 본문을 출력하지 않으므로 무효. **삭제하지 않고 "왜 스크립트로 갔는가"의 근거로 축약 보존** |

§6.4를 지우지 않는 이유는, 그 실패 기록이 이 전환의 근거 자체이기 때문이다.
지우면 왜 스크립트인지가 위키에서 사라진다.

**개정 시 함께 고칠 오류 1건** — §6.4 ③의 "§6.1 구조의 부모는 12개뿐"은 틀렸다.
페이지를 받는 부모는 **13개**다(§6.3의 `*` 표시 참조). 2026-08-16 건강검진이
반복해서 잡아낸 수기 집계 불일치와 같은 유형이며, 설계 중 실측으로 발견했다.

## 9. 검증

**단위** — HTTP 없이 검증 가능한 순수 함수로 분리한다.

| 대상 | 방법 |
|---|---|
| 증분 판정 | null / 같은 날 / 이전 / 이후 4가지 입력 |
| 배치 결정 | 35개 전 페이지에 대해 기대 부모와 대조. 미완 과제 절 링크가 무시되는지 포함 |
| 엔진 분기 | `엔진별 운영` 12개 + 충돌·무태그 경계 케이스 |
| HOLD 검사 | 절 제목 차집합 — 동일/추가/삭제 3가지 |
| 인증 가드 | `.env`가 추적 중일 때·퍼미션이 644일 때 종료하는지 |

**통합** — `--dry-run`으로 35개 전체 계획을 출력해 눈으로 확인한 뒤 카나리 1건.

## 10. 미해결

- **휴지통 정리**: 삭제된 32개가 휴지통에 남아 Notion 검색 결과에 나타난다.
  영구 삭제는 사용자 판단이며 스크립트는 관여하지 않는다.
- **`기술 문서` 소실**: §6이 "위키가 만든 것이 아닌 기존 자료 — 건드리지 않는다"고
  보호하던 페이지도 함께 삭제됐다. 복구 필요 여부는 사용자 확인 대상.
- **대용량 페이지**: `allow_async: true`와 폴링이 필요한 임계가 문서에 명시돼 있지
