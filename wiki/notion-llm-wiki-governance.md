# Notion DBA 포털 운영 거버넌스

## 핵심 구조 (3계층)

1. **원본 계층** — 과거 Notion 페이지, 공식 문서, 장애 기록. 불변, 삭제 금지. 출처 URL·수집일·버전·환경 추적.
2. **정제 위키 계층** — 영역별 대표 페이지가 상세 본문의 공식 위치. `Muto Knowledge Base`(DB)는 본문 저장소가 아니라 **색인 전용** (제목·요약·영역·상태·마지막 검증일·본문 링크만).
3. **운영 스키마 계층** — 운영 지침 + 정리 원칙 문서 자체가 LLM 작업 규칙.

## 문서 상태 모델

`검증 완료`(공식 문서/실행 검증) → `검토 필요`(개념 유효, 버전·환경 미확인) → `업데이트 필요`(현재 동작과 다를 가능성 큼) → `보관`(역사적 참고, 대체 문서 링크 필수).

## 핵심 운영 원칙

- 한 주제 = 한 대표 문서. 같은 본문을 색인과 본문 페이지에 중복 복사하지 않는다.
- 충돌은 삭제 사유가 아님: 버전 차이 / 환경 차이 / 실제 사실 충돌을 구분하고 양쪽 주장과 근거를 기록.
- 실행 명령·SQL은 대상 DBMS·버전·배포 형태·트랜잭션 영향·롤백을 명시. 파괴적 명령은 안전 확인 절차와 최소 권한 대안을 먼저 둔다.
- PostgreSQL OSS / RDS / Aurora처럼 이름이 비슷한 제품은 적용 환경으로 분리해서 기술한다.
- 완료 기준: 대표 문서 갱신 + 버전·환경 표시 + 출처 연결 + 색인 갱신 + 충돌·위험 상태 표시 + 보안 검사 + 변경 기록.

## 보완·수정 사항 (분석 결과)

- **[보완] 이중 시스템 문제**: Notion 포털과 로컬 Obsidian 볼트(second-brain)가 같은 역할(DBA 지식 정제)을 하게 됨. 역할 분리 필요 — 예: Notion = 팀 공유·검증 완료 지식, 로컬 볼트 = 개인 작업 로그·초안·커리어 기록. 정하지 않으면 이중 관리 부담과 드리프트 발생. ^[inferred]
- **[수정] 상태 집계의 수기 드리프트**: 보고서의 집계(17/7/0/7)가 "Query Data Source 사용량 한도로 자동 재조회 보류, 직전 값에서 수기 반영"으로 계산됨. 수기 누적은 오차가 쌓이므로 주기적으로 DB 뷰 기준 재집계로 보정해야 한다.
- **[보완] Query 절차의 과도한 확인 단계**: 검색 실패 시마다 사용자에게 조사 방식을 묻는 규칙은 실무에서 마찰이 큼. "운영 명령·보안 관련은 반드시 확인, 일반 지식은 LLM 판단 허용"으로 완화하는 편이 지속 가능. ^[inferred]
