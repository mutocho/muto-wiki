> - **규칙 파일은 반드시 하나다.** 같은 규칙을 두 파일에 쓰면 반드시 갈라진다. 현재는 `CLAUDE.md`가 실체이고 `AGENTS.md`가 그 심볼릭 링크 — Claude와 Codex가 같은 바이트를 읽는다

> - **기술 지식과 업무 기록은 같은 페이지에 두지 않는다.** 전자는 이직 후에도 쓰는 자산, 후자는 성과 정리 원천이다. 수명이 다르므로 분리하고 링크로 잇는다
> - 결정을 바꿀 때는 이 페이지를 덮어쓰지 말고 아래 "변경 이력"에 추가한다 — 왜 그렇게 됐는지가 결정 자체보다 오래 쓸모 있다

# 위키 거버넌스 결정 — 적재 라우팅·에이전트 규칙 단일화·브랜치 금지

## Context

볼트를 여러 장비·여러 에이전트(Claude Code, Codex)에서 쓰고, 이직 후에도 career 기록을 이어가려면 적재 구조와 규칙 파일의 단일 소스가 필요했다.

## Decision

1. **기술 지식과 업무 기록을 분리 적재한다** — 재사용 가능한 기술 지식은 `db운영`, 회사에서 수행한 작업 기록은 `업무기록`. 하나의 사건이 양쪽에 해당하면 페이지를 나누고 `[[링크]]`로 상호 연결한다. 연도별 업무 로그는 `worklog-<회사>-<연도>` 한 페이지에 월 단위로 누적한다.
2. **에이전트 규칙은 파일 하나가 단일 소스다** — 현재는 `CLAUDE.md`가 실체이고 `AGENTS.md`는 그 심볼릭 링크다. Claude Code와 Codex가 같은 바이트를 읽으므로 구조적으로 드리프트가 불가능하다. 규칙 중복을 두지 않는다.
3. **이 저장소는 브랜치를 생성하지 않는다** — 모든 커밋은 main 직접 수행. `scripts/sync.sh`가 main에 커밋하므로 브랜치를 만들면 자동 동기화 커밋과 갈라져 관리 비용만 생긴다. ^[inferred]
4. **충돌은 원격이 우선한다** — 여러 장비에서 쓰는 개인 위키에서는 다른 기기가 올린 내용이 로컬의 작업 중 상태보다 신뢰도가 높다. `sync.sh`가 `-X theirs`로 해소한다.

## Reasoning

- 기술 지식과 업무 기록은 **수명이 다르다.** 전자는 이직 후에도 유효하고 후자는 그 시기·조직에 묶인다. 한 페이지에 섞으면 둘 다 못 쓰게 된다.
- 규칙을 두 파일에 쓰면 드리프트가 생긴다. 문서로 "동기화하세요"라고 적는 대신 **심볼릭 링크로 구조상 불가능하게** 만드는 편이 안전하다.
- 폴더 계층 대신 `category` 필드와 [[index]] 분류를 쓰면, 분류 기준이 바뀌어도 파일을 옮기지 않아도 된다 — wikilink가 깨지지 않는다. ^[inferred]

## Implications

- `wiki/`에 하위 폴더를 만들지 않는다. 분류가 필요하면 [[index]]의 카테고리 절을 고친다.
- 커밋 워크플로우 스킬(`/commit-push-pr` 등)이 브랜치를 만들려 해도 main 직접 커밋으로 대체한다.
- Codex처럼 훅이 없는 환경에서는 `scripts/sync.sh pull` / `push`를 직접 실행해야 한다 — 규칙 파일에 명시돼 있다.
- 이직 시에는 `worklog-<새회사>-<연도>` 페이지를 새로 만들 뿐, 기존 기록을 건드리지 않는다.

## 변경 이력

- **2026-08-15** — llm-wiki(`second-brain/`)에서 이 저장소로 이전하며 구조 변경. ① 폴더 계층(`dba/`, `career/<회사>/`, `personal/`) → **플랫 `wiki/` + `category` 필드**. ② 규칙 단일 소스를 `AGENTS.md` + `CLAUDE.md @import` → **`CLAUDE.md` 실체 + `AGENTS.md` 심볼릭 링크**로 반전(`@import`는 Codex가 따라가지 못한다). ③ 모든 페이지에 Takeaway callout 의무화. ④ 자동 동기화를 저장마다 커밋 → **열 때 pull / 마칠 때 push**로 변경.
- **2026-08-06** — 최초 결정. career 회사 단위 폴더 라우팅, `AGENTS.md` 단일 소스, 브랜치 금지.
